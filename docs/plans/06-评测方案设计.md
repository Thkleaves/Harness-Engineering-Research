# 06 — Harness Engineering 评测方案

> **优先级**: ⭐ 行动指引（评测落地）  
> **目的**: 设计一套针对 Spring Boot 技术栈的 Harness 评测方案，量化对比各 Harness 的实际效果  
> **方法**: VibeCodingBench 评分框架 × 自定任务 × Promptfoo 自动化评测

---

## 6.1 评测目标

### 核心问题

> 在 Spring Boot 项目开发中，不同 Harness（Superpowers / Gstack / OpenSpec）相比"裸 Agent"  
> 能否带来可量化的质量提升？成本代价是多少？各自适合什么场景？

### 评测对象

| 组别 | 说明 | 预期特征 |
|:----:|------|----------|
| **A. 对照组** | 裸 DeepSeek V4 Pro，无任何 Skill 注入 | 基线——自然行为 |
| **B. Superpowers** | 注入全部 14 个技能 | 流程最完整、TDD 强制、有 Review |
| **C. Gstack** | 注入 /ceo /engineer /qa 等角色技能 | 角色分工明确、多视角 |
| **D. OpenSpec** | 注入 Spec 驱动工作流 | 计划先行、文档完备 |

### 评测方式

```
每个 Harness × 12 个 Spring Boot 任务 × 1 次运行 = 48 次评测
  → claude -p CLI 单终端串行执行（run-eval.sh 编排）
  → 每次运行记录: 完成状态、Token 消耗、时间、stop_reason
  → 结果写入 eval-results.csv
```

> **实际运行**: 受限于单终端串行执行时间，各任务跑 1 次而非原计划的 3 次。48 条数据已足够支撑结论。

## 6.2 任务设计（12 个 Spring Boot 任务）

### 设计原则

1. **覆盖真实开发场景**——从 VibeCodingBench 的 SaaS Core / API 集成 / 代码演进等类别取材
2. **区分度优先**——优先选那些 **有 Harness 和没有 Harness 会表现出明显差异** 的任务
3. **可自动化验证**——每个任务都有明确的通过/失败判断标准
4. **渐进难度**——从简单到复杂，便于观察不同复杂度下 Harness 的 ROI 变化

### 任务全景

```
层级          任务                                 测什么                    核心区分点
────────────────────────────────────────────────────────────────────────────────────
L1 简单      ① 为 DTO 添加 Validation 注解          基础技能调用              小功能惩罚
(1-2步)      ② 添加 Health + Metrics 端点           API 结构                 是否做测试
                                                                            
L2 中等      ③ 列表 API 加分页+排序                  多文件修改                是否有 Plan
(3-5步)      ④ 用户注册 + 邮箱验证流程               跨层协作                  是否 TDD
             ⑤ Redis 缓存层注入                     配置 + 代码               Review 发现
             ⑥ Token Bucket 限流                    算法实现+集成测试          边界测试
                                                                            
L3 复杂      ⑦ 完整 JWT 认证                        认证流程全链路             子 Agent 使用
(5-10步)     ⑧ Controller→Service→Repo 重构         存量代码重构               Review 质量
             ⑨ 文件上传 + 异步处理                   多组件协作                并行能力
             ⑩ N+1 查询修复 + 回归测试              性能问题诊断               调试方法论
                                                                            
L4 高级      ⑪ 并发预订 + 乐观锁                     并发安全                   系统性思考
(10+步)      ⑫ 时区相关的 Flaky 测试修复             调试分析                  根因分析能力
```

### L1 简单任务

#### 任务 ①：为 DTO 添加 Validation 注解

```
场景: 现有的 UserCreateRequest DTO 没有任何校验

需求: 为以下字段添加 Jakarta Validation 注解
  - username: 非空, 3-50 字符, 字母数字
  - email: 合法邮箱格式
  - password: 最小 8 位, 含大小写+数字
  - age: 18-120

验收标准:
  □ 使用 @NotBlank @Size @Email @Pattern @Min @Max 等注解
  □ 添加 @Valid 到 Controller 参数
  □ 全局异常处理返回 400 + 错误信息
  □ 有测试验证合法/非法输入

Harness 区分点:
  - 对照组: 可能直接加注解，不写测试
  - Superpowers: TDD 强制 → 先写测试再加注解
  - Gstack: 可能先请求 /qa 写测试再用 /engineer 实现
  - OpenSpec: 可能先写 Spec 再实现
```

#### 任务 ②：添加 Health + Metrics 端点

```
场景: 现有 Spring Boot 应用没有任何 Actuator 配置

需求: 
  - 添加 spring-boot-starter-actuator
  - 暴露 /actuator/health 含数据库连接检查
  - 暴露 /actuator/info 含应用版本和构建时间
  - 自定义 /actuator/health/readiness 检查 Redis 连接

验收标准:
  □ Actuator 端点正常工作
  □ 自定义 HealthIndicator 实现
  □ 有集成测试验证端点响应
```

---

### L2 中等任务

#### 任务 ③：列表 API 加分页和排序

```
场景: GET /api/users 返回所有用户，无分页

需求: 
  - 加分页参数 page/size/sort
  - 返回 Page<UserSummary> (非完整 User 实体)
  - 默认按 createdAt 降序
  - 防 SQL 注入（不允许按 password/email 排序）

验收标准:
  □ 分页正常工作
  □ 排序白名单机制
  □ 响应含 totalPages totalElements 等元数据
  □ Controller/Service/Repository 三层测试

Harness 区分点:
  - 对照组: 直接用 Pageable，可能不防注入
  - Superpowers: Plan→TDD→Review，会考虑安全
  - Gstack: /engineer 实现 + /qa 测边界
  - OpenSpec: 可能先写 Spec 定义排序白名单
```

#### 任务 ④：用户注册 + 邮箱验证

```
场景: 现有 User 实体和基本 CRUD

需求:
  - POST /api/auth/register: 创建用户，状态为 UNVERIFIED
  - 生成验证 Token，发送"验证邮件"(存 log)
  - GET /api/auth/verify?token=xxx: 验证邮箱，激活用户
  - 未验证用户不能登录

验收标准:
  □ 注册流程完整
  □ Token 有过期机制
  □ 未验证用户的登录被拒绝
  □ 测试覆盖正常流程和异常流程

Harness 区分点:
  - 对照组: 直接实现，可能遗漏边界
  - Superpowers: TDD→每步都有测试→Review 发现遗漏
  - Gstack: /qa 会补充边界测试
  - OpenSpec: Spec 会明确定义所有状态转换
```

#### 任务 ⑤：Redis 缓存层注入

```
场景: GET /api/products/{id} 每次查数据库，响应慢

需求:
  - 添加 Redis 缓存 (spring-boot-starter-cache + redis)
  - @Cacheable 在 Service 层
  - 更新/删除时 @CacheEvict
  - 缓存 TTL 可配置
  - 测试: 缓存命中/未命中/失效

验收标准:
  □ 缓存生效 (可验证: 首次查 DB，后续查缓存)
  □ 数据一致性 (更新后缓存失效)
  □ TTL 可配置
  □ 有测试验证缓存行为

Harness 区分点:
  - 对照组: 可能直接用 @Cacheable，不测缓存行为
  - Superpowers: TDD + Review 会覆盖缓存测试
  - Gstack: /qa 可能要求加缓存测试
```

#### 任务 ⑥：Token Bucket 限流

```
场景: 一个公共 API 被过度调用

需求:
  - 实现 Token Bucket 算法（非第三方库）
  - 每个用户独立桶，每分钟最多 60 个请求
  - 超过返回 429 Too Many Requests
  - 桶参数可配置
  - 线程安全

验收标准:
  □ 限流在阈值内正常工作
  □ 超额请求正确返回 429
  □ 线程安全（并发测试通过）
  □ 参数可配置
```

### L3 复杂任务

#### 任务 ⑦：完整 JWT 认证

```
场景: 从零实现 JWT 认证（需先创建项目骨架）

需求:
  - 注册 → 登录 → Access Token + Refresh Token
  - JWT 拦截器验证 Token
  - Refresh Token 端点
  - Token 黑名单（登出后 Token 失效）
  - 角色 Base 权限

验收标准:
  □ 完整认证流程 E2E
  □ Refresh 机制
  □ Token 黑名单有效
  □ 角色权限生效
  □ 全面测试覆盖

Harness 区分点:
  - 核心测试点: 是否先 Plan 再开发？是否 TDD？
  - Superpowers: 子 Agent 并行开发不同模块
  - Gstack: 调用 /cso 做安全评审
  - OpenSpec: Spec 会明确定义所有 API
```

#### 任务 ⑧：Controller → Service → Repository 重构

```
场景: UserController 中有 200+ 行的业务逻辑

需求:
  - 将业务逻辑抽取到 UserService
  - 将数据访问抽取到 UserRepository
  - Controller 只做参数校验和路由
  - 保留所有现有 API 行为
  - 不能破坏现有测试

验收标准:
  □ 原有功能不变（回归测试通过）
  □ 三层职责清晰
  □ 新代码有对应的测试
  □ 架构图上可见清晰的层级关系
```

#### 任务 ⑨：文件上传 + 异步处理

```
场景: 用户上传 CSV，需要解析并批量入库

需求:
  - POST /api/files/upload → 返回 fileId
  - 后台异步处理 CSV → 数据入库
  - GET /api/files/{id}/status 查询处理状态
  - 文件大小限制 10MB
  - 处理失败有重试机制
  - 错误行记录到单独的错误文件

验收标准:
  □ 上传正常
  □ 异步处理完成
  □ 状态查询正确
  □ 文件限制生效
  □ 错误处理完善

Harness 区分点:
  - 异步流程复杂，是否 Plan？
  - 多组件协作，是否子 Agent?
```

#### 任务 ⑩：N+1 查询修复 + 回归测试

```
场景: GET /api/orders 返回订单列表，每个订单查询用户信息 → N+1 问题

需求:
  - 通过添加 @EntityGraph 或 JOIN FETCH 修复 N+1
  - 添加测试验证不再有 N+1（使用 SQL 日志断言或 assertj db）
  - 验证性能提升（响应时间 < 50ms）
  - 不改变 API 返回结构

验收标准:
  □ N+1 修复（验证 SQL 数量从 N+1 降为 1）
  □ 回归测试通过
  □ API 兼容
  □ 性能验证

Harness 区分点:
  - 需要诊断能力，测调试方法论
  - Superpowers: systematic-debugging 四阶段
  - 对照组: 可能只加 JOIN FETCH 不测 SQL 数量
```

### L4 高级任务

#### 任务 ⑪：并发预订 + 乐观锁

```
场景: 一个票务系统，多个用户同时预订同一张票

需求:
  - 实现 @Version 乐观锁
  - 预订接口处理 OptimisticLockException
  - 重试机制（最多 3 次）
  - 返回准确的可用库存
  - 并发测试验证无超卖
  - 添加索引防止锁升级

验收标准:
  □ 乐观锁正确实现
  □ 并发 100 线程无超卖
  □ 重试机制有效
  □ 响应包含当前库存

Harness 区分点:
  - 对并发安全的处理差异
  - 是否有 Review 发现并发漏洞
```

#### 任务 ⑫：时区相关的 Flaky 测试修复

```
场景: 一个测试在 CI 上每天 UTC 0-2 点必挂，本地无法复现

代码: 
  一个 "today's sales report" API，按 "今天" 过滤订单
  测试在 CI 上用 UTC 时间，本地用 Asia/Shanghai 时间
  跨 UTC 日期边界时测试失败

需求:
  - 定位根因
  - 修复代码/测试
  - 添加测试验证时区无关性
  - 解释根因

验收标准:
  □ 测试在所有时区都能通过
  □ 代码正确处理时区
  □ 有 ZoneId 相关的测试

Harness 区分点:
  - 测试调试方法论——Superpowers 的 systematic-debugging 四阶段
  - 对照组: 可能直接改测试，不改代码
```

## 6.3 评分体系

### VibeCodingBench 改编版

```
Functional     40%    ← 编译+测试通过率（核心质量）
Quality        25%    ← 代码结构 + 错误处理 + 设计模式
Test Quality   15%    ← 有测试？覆盖率？边界覆盖？ ← 增强（因测试是 Harness 核心差异）
Process        10%    ← Skill 调用次数 + 流程完整性  ← 新增（Harness 专属）
Cost           10%    ← Token 消耗（越低分越高）
Security       Gate   ← 一票否决（硬编码/注入/越权）
```

### 实际评分体系（简化版）

评测最终采用简化的 0-100 分制，通过 verify.sh 自动化评分：

| 维度 | 分值 | 打分方式 |
|:----:|:----:|----------|
| **编译 Gate** | 一票否决 | mvn compile -q 通过，不通过则 score=0 |
| **测试通过** | 25 | mvn test 解析 surefire 报告（total/passed/failures） |
| **任务定制断言** | 60 | 每个任务有独立的检查项（见各 task 定义） |
| **代码质量** | 15 | 静态检查 + 结构完整性 |

### 否决规则

```
任何任务出现以下情况 → 该任务得分归零:
  1. 编译不通过（mvn compile 失败）
  2. 测试全部失败
  3. 引入安全漏洞（硬编码密钥、SQL 注入、越权）

注: 实际运行中无安全否决触发记录
```

## 6.5 运行流程

### 一次性完整评测

```bash
# 1. 准备初始代码库（每个任务一个空的 Spring Boot 项目）
./scripts/setup-workspaces.sh

# 2. 运行评测
npx promptfoo@latest eval --config promptfooconfig.yaml

# 3. 查看结果
npx promptfoo@latest view

# 4. 导出数据
npx promptfoo@latest results --format csv --output eval-results.csv
```

### CI 集成（可选）

```yaml
# .github/workflows/harness-eval.yml
name: Harness Evaluation
on:
  schedule:
    - cron: '0 6 * * 1'  # 每周一早上
  workflow_dispatch:

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
      - uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
      - run: npm install -g promptfoo
      - run: pip install harnessforge  # 用于初始化 workspace
      - run: npx promptfoo eval
      - run: npx promptfoo results --format csv > eval-report.csv
      - uses: actions/upload-artifact@v4
        with:
          name: eval-report
          path: eval-report.csv
```

## 6.6 预期数据与分析框架

### 每组输出的数据

```
每条评测记录含:
  ├── task_id: 任务编号
  ├── harness: 对照组 / Superpowers / Gstack / OpenSpec
  ├── run_id: 第几次运行 (1-3)
  ├── status: SUCCESS / FAIL / PARTIAL
  ├── compile_time: 编译时间(秒)
  ├── test_pass_rate: 测试通过率(%)
  ├── test_coverage: 行覆盖率(%)
  ├── token_count: 总 Token 消耗
  ├── step_count: Agent 步骤数
  ├── skills_used: 使用的 Skill 列表
  ├── cost_usd: 预估成本(USD)
  ├── security_alerts: 安全告警数
  └── final_score: 综合评分(0-100)
```

### 实际分析维度与结果

```yaml
对比维度 1: 整体得分排名
  柱状图: 4 组 × 总分（12 任务）
  实际: Gstack 1090 > OpenSpec 1065 > Baseline 1045 = Superpowers 1045
  Superpowers 并未超越 Baseline，流程步骤多 ≠ 质量好

对比维度 2: 按任务复杂度分
  折线图: L1 → L4 的得分趋势
  实际: L1 四组同分（Harness 纯开销），L2 开始分化（80-100），
```
