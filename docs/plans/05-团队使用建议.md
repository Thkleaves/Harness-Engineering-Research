## 5.1 团队现状评估

在引入 Harness Engineering 前，建议先评估团队在以下维度上的成熟度：

### 评估矩阵

| 维度 | L1 初始级 | L2 规范级 | L3 工程级 | L4 优化级 |
|------|:---------:|:---------:|:---------:|:---------:|
| **Agent 使用** | 个人尝试 | 团队统一工具 | 标准化流程 | 持续优化 |
| **上下文管理** | 无 | 有 CLAUDE.md | 分层上下文 | 自动 GC |
| **测试习惯** | 不测试 | 有测试但不强制 | TDD/BDD 强制 | 自动化验证 |
| **代码审查** | 偶尔 | 有但形式化 | 结构化评审 | 多维自动化 |
| **工具治理** | 无 | 基本授权 | 风险分级 | 运行时守卫 |
| **团队协作** | 各自为战 | 共享规范 | Worktree 隔离 | 全流程可观测 |

> **评估方法**: 对每个维度打分（L1=1, L2=2, L3=3, L4=4），总分 <12 建议从基础开始，>18 可考虑企业级方案。

## 5.3 分阶段详细任务

### Phase 1：准备期（第 1-2 周）

#### 目标
- 团队对 Harness Engineering 建立统一认知
- 确定试点项目和工具链
- 完成环境准备

#### 任务清单

```markdown
□ 团队分享本报告内容（建议 1h 技术分享）
   - 重点章节: 01-概念与背景, 02-工具调研与对比

□ 确定 1-2 个试点项目
   - 选择标准: 非关键业务、有完整开发流程、团队配合度高
   - 排除标准: 紧急交付中的项目、遗留系统重构

□ 试点团队确定
   - 建议 2-3 人，至少 1 人对 Agent 编码有经验
   - 指定负责人协调工具安装和问题反馈

□ 环境准备
   - Claude Code 最新版
   - Superpowers 插件安装（参考 03-01）
   - Git Worktree 概念理解
```

#### 里程碑检查

- [ ] 团队 80% 成员了解 Harness Engineering 基本概念
- [ ] 试点项目确定并得到相关方确认
- [ ] 开发环境已安装 Superpowers
- [ ] 已在小项目上跑通一次完整流程

## 5.4 ROI 评估框架

### 量化收益指标

| 指标 | 测量方法 | 基线 | 目标 |
|------|----------|:----:|:----:|
| 功能交付时间 | 从需求到合并的日历时间 | 当前 | -30% |
| 测试覆盖率 | 代码覆盖率报告 | 当前 | 85%+ |
| 返工率 | 因设计遗漏导致的返工比例 | 当前 | -50% |
| 缺陷密度 | 每千行代码的 Bug 数 | 当前 | -40% |
| 新成员上手时间 | 从进组到独立交付功能 | 当前 | -50% |

### 量化成本指标

| 指标 | 说明 | 估算 |
|------|------|:----:|
| Token 增量成本 | Harness 流程本身消耗的 Token | ~20-30% 额外 |
| 学习投入 | 团队学习 Harness 工具的时间 | ~每人 2-3 天 |
| 配置维护 | 配置文件持续更新 | ~每周 0.5h |

### ROI 决策点

```
问题: Harness Engineering 值得投入吗？

团队人均 Agent Token 月消耗 >= $200？
├── 是 → 引入 Harness 可能节省 30-50% 浪费的 Token
│         → 预计 2-4 周内 ROI 为正
└── 否 → 团队 Agent 使用频率不高？
        ├── 是 → 建议先提高 Agent 使用率，再引入 Harness
        └── 否 → 引入 Harness 主要靠质量提升（非成本节省）回本
                 → ROI 周期 4-8 周
```

## 5.5 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|:----:|:----:|----------|
| **工具学习曲线陡峭** | 中 | 高（团队抵触） | 分阶段引入，先核心技能 |
| **Token 开销焦虑** | 高 | 中 | 透明展示 ROI 数据 |
| **流程过于僵化** | 中 | 高（降低效率） | 允许按场景跳过某些步骤 |
| **团队抵触变化** | 中 | 高 | 让试点团队数据说话 |
| **工具版本不稳定** | 低 | 中 | 锁定已知稳定版本 |
| **过度依赖 Agent** | 低 | 高 | 保持人肉 Review |

## 5.6 常见问题 FAQ

### Q1: Harness Engineering 会影响我们的现有流程吗？

不会。Harness Engineering 是 **叠加** 在现有流程之上的。你可以先在一个小项目上试点，不影响主干流程。

### Q2: 引入 Harness 会增加多少 Token 成本？

约 20-30% 的额外 Token 消耗。但同时会减少 30-50% 的浪费 Token（如 Agent 做无关探索、写无用代码）。净效果取决于项目复杂度，通常在大项目中 **净节省**。

### Q3: 我们用的是 Codex / Cursor 不是 Claude Code，兼容吗？

Superpowers 官方支持 Codex CLI、Cursor、GitHub Copilot CLI。HarnessForge 支持所有 Agent（生成 AGENTS.md 格式）。

### Q4: 小型团队（1-2人）有必要吗？

有必要，但可以简化。建议只使用 Superpowers 的核心技能（Brainstorming → Plans → TDD），跳过团队协作相关的部分（如 Git Worktree、并行调度）。

### Q5: 如何让团队接受这个变更？

- 让团队参与试点（而不是自上而下推行）
- 用数据说话（试点期的量化对比）
- 从"解决痛点"角度引入，而不是"引入新工具"
- 先解决团队最痛的问题（如"总在 Review 发现低级错误"→ TDD 强制）

## 5.7 核心建议总结

> **注意**: 以下建议综合了 Day 1 实操体验和 Day 3 量化评测数据。

### 场景化选择（基于评测数据）

| 场景 | 推荐 | 理由 |
|------|:---:|------|
| 需求明确、无歧义的简单任务 | **裸Agent** | 最快、token 最低、质量不差。L1 四组同分 |
| 多技术点组合 | **Gstack** | 多角色视角覆盖最全，1090 分排名第一 |
| API 设计 / 状态机 | **OpenSpec** | Spec 驱动在接口定义上有系统性优势 |
| 算法实现 + 测试密集 | **Superpowers** | TDD 在代码正确性可被测试验证时最强 |
| 存量代码重构 | **各组同分** | L3 四组 100，裸Agent 一次做对 |
| 全局重构（改旧代码） | **全部不足** | 任务⑫ 四组 70 分，Agent 怕改旧代码 |

### 关键认知

1. **流程步骤多 ≠ 质量好** — Superpowers 14 技能全流程，总分与裸 Agent 持平
2. **角色分工 > 流程约束** — Gstack 的 CEO/Engineer/QA/DevOps 多视角 > Superpowers 的单人 5 步流程
3. **Harness 价值需要交互释放** — 自动评测中禁止提问，Harness 的 brainstorming 退化成了自问自答
4. **不要在小任务上用重 Harness** — L1 上四组同分，Harness 是纯 Token 开销
