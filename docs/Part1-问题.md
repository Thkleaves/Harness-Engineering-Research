# Part 1：问题 —— AI 编码的瓶颈已从模型转向工程化

---

## 1.1 一个真实场景

```
你: "帮我给 Book API 加个参数校验，别让空数据进来。"
AI:  "好的。" → 加了 @NotBlank，完事。
```

**你漏了什么？**

| 漏掉的东西 | 后果 |
|-----------|------|
| ISBN 格式没校验 | `"abc"` 通过，脏数据入库 |
| 价格没小数位控制 | `9.999` 入库，财务对不上 |
| PUT 部分更新不校验 | 传入空字段直接覆盖已有数据 |
| 错误响应是 Tomcat 默认 HTML 页面 | 前端解析不了，用户体验差 |
| 没写测试 | 下次重构时静默退化，没人知道 |

这六个字"别让空数据进来"，裸 Agent 只理解了字面意思——**别是 null**。

加上 Superpowers 的 brainstorming，它会用 **6 轮苏格拉底式追问**把这句话展开成：

| # | 追问 | 结论 |
|---|------|------|
| 1 | 哪些字段必填？ | title、author、isbn、price 全部 |
| 2 | "不为空"的粒度？ | 非 null + 去首尾空格后不为空 |
| 3 | price 额外约束？ | 非 null + >0 + 最多两位小数 |
| 4 | isbn 格式？ | 去连字符后必须 10 或 13 位数字 |
| 5 | 错误响应格式？ | 结构化 JSON，一次返回全部字段错误 |
| 6 | PUT 更新行为？ | 部分更新，传入的字段校验，null 跳过 |

**同一模型。同一需求。结果天差地别。**

---

## 1.2 核心论点

```
传统认知:  AI 编码质量 = f(模型能力)
实际情况:  AI 编码质量 = f(模型能力 × 工程化框架)
                    ↑                    ↑
               天花板由模型定        落地效果由 Harness 定
```

LangChain 在 Terminal-Bench 2.0 上的实验已经证实：

| 优化方式 | 得分提升 | ROI |
|---------|:------:|:---:|
| 升级模型（GPT-4 → Claude 4） | +5.2% | 低（模型升级持续烧钱） |
| **Harness 优化**（架构 + hook + skill） | **+13.7%** | 高（工程优化一次投入） |

> **模型是引擎，Harness 是让它可控行驶的底盘。** 引擎再好，底盘松散的车也开不稳。

## 1.3 Harness Engineering 是什么

```
┌─────────────────────────────────────────────────┐
│               Harness Engineering               │
│                                                 │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │   上下文管理   │  │   流程引导    │  │   质量护栏    │  │
│  │              │  │              │  │              │  │
│  │ · 记忆系统   │  │ · 需求澄清    │  │ · 安全扫描    │  │
│  │ · 文档沉淀   │  │ · 实现计划    │  │ · 测试强制    │  │
│  │ · 项目认知   │  │ · 代码审核    │  │ · 编译验证    │  │
│  └──────────────┘  └──────────────┘  └──────────────┘  │
│                                                 │
│  一句话: 确保模型在正确的时机做正确的事                    │
└─────────────────────────────────────────────────┘
```

Harness 不是"教模型写代码"——模型本来就会。它是**在模型会写的基础上，确保它先想清楚再动手、先写测试再实现、写完自证能跑。**

## 1.4 第二个翻车案例 —— 从零构建短链接服务

不只修改已有代码会翻车，**从零构建新项目时 Agent 的"默认选择"同样不可靠**。

我们让裸 Agent 从零构建一个 URL 短链接服务（Spring Boot + Java 21）。结果：

```
Agent 自选了 Base62 自增 ID → 短码可预测，暴露内部计数
  没有幂等策略         → 同一 URL 创建 10 次 = 10 个不同短码
  统计只记次数         → 没有时间轴，没有 Referer/User-Agent
  没有 Clock 注入      → 测试无法模拟时间推进
  测试 13 个           → 能跑，但漏了 24h 去重、碰撞重试等关键场景
```

**能跑。但完全不是用户想要的。**

而同样的项目，给 Agent 加上 Harness 流程引导 + **允许跟用户交互**（3 轮需求澄清），结果完全不同：

| 决策 | 裸 Agent | Harness + 交互 |
|------|:---:|:---:|
| 短码算法 | Base62 自增 | **随机 7 位 SecureRandom** |
| 幂等策略 | 无 | **24h 去重窗口** |
| 统计粒度 | 计数 | **时间戳 + Referer + UA，100 条** |
| 时钟注入 | 无 | **Clock 注入** |
| 测试数 | 13 | **19** |

**同一模型。同一需求。唯一区别是有没有人告诉 Agent 真正要什么。**

## 1.5 一个问题

> 如果 Harness 这么好，为什么我们的评测里 Superpowers 总分和裸 Agent 一样？

答案分两层：

1. **自动评测中 Agent 被禁止向用户提问**——Harness 的 brainstorming 退化成了"自问自答"。Agent 猜了一个合理默认值（"自增 ID 吧"），但这不是用户想要的（"随机码 + 24h 幂等"）
2. **Harness 的价值因场景而异**——评测数据表明，不同任务难度和类型下，各组 Harness 的表现差异巨大

后面 Part 3 的数据会展开讲。
