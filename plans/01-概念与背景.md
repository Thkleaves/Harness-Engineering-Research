# 01 — 什么是 Harness Engineering

> **优先级**: ⭐ 核心基础（所有人必读）  
> **目的**: 建立对 Harness Engineering 的统一认知

---

## 1.1 背景：AI 编码的演进路径

```
2023           2024             2025              2026
┌──────┐    ┌────────┐    ┌──────────┐    ┌──────────────┐
│ 补全  │ → │ Chat   │ → │ Agent 编码 │ → │ 工程化 Harness │
│ Copilot│   │ Cursor │   │ Claude   │    │ Agent = 模型  │
│       │   │ Claude │   │ Codex    │    │     + 底盘    │
└──────┘    └────────┘    └──────────┘    └──────────────┘
```

**关键转折点（2026.02）**：OpenAI 发布论文 *"Harness Engineering: Leveraging Codex in an Agent-First World"*，正式定义了这个领域。核心论点：

- AI 编码代理（Agent）已经能写代码，但**缺乏工程化约束**导致输出不可控
- 未来的瓶颈不在模型能力，而在于**围绕 Agent 构建的工程化基础设施**
- Harness Engineering 是 Agent 时代的"软件工程"——从关注代码质量转向关注 **Agent 行为质量**

---

## 1.2 定义

**Harness Engineering** 是指为 AI 编码代理（Coding Agent）构建 **工程化运行环境** 的实践体系。它包含：

| 层 | 说明 | 类比 |
|----|------|------|
| **上下文管理** | 分层的、渐进式暴露的项目上下文 | 传统 IDE 的项目文件树 |
| **工具治理** | 按风险等级分类管控 Agent 可用工具 | 操作系统的权限管理 |
| **安全护栏** | 运行时守卫、输出验证、敏感操作审批 | 数据库的事务日志 |
| **编排调度** | Plan→Execute→Review 工作流编排 | CI/CD 的 Pipeline |
| **可观测性** | Agent 行为追踪、成本监控、性能度量 | APM 监控系统 |
| **记忆系统** | 跨会话持久化、经验积累、错误记忆 | 人的长期记忆 |
| **质量门禁** | 代码审查、测试强制、验证前置 | 代码审查门禁 |

---

## 1.3 为什么要关注 Harness Engineering

### 🎯 核心驱动：模型能力趋同，Harness 成为差异化因素

LangChain 在 Terminal-Bench 2.0 上的实证表明：

| 变更 | 得分变化 |
|------|:--------:|
| 模型升级（Claude 3.5 → 4.0） | +5.2% |
| Harness 优化（改进上下文、工具选择） | **+13.7%** |
| Harness + 无模型变更 | 52.8% → **66.5%** |

> 结论：**改进 Harness 的 ROI 高于升级模型。**

### 🚨 痛点场景（没有 Harness 时的常见问题）

| 痛点 | 频率 | 根因 |
|------|:----:|------|
| Agent 忘记项目上下文，产生不一致代码 | 极高 | 无结构化上下文管理 |
| Agent 过度修改无关文件 | 高 | 无范围约束 |
| 反复犯相同错误 | 高 | 无错误记忆机制 |
| 生成的代码没有测试 | 中 | 无流程强制 |
| Token 浪费在无关探索上 | 极高 | 无计划前置 |
| 难以复现之前的成功模式 | 中 | 无模式记录 |

## 1.4 Harness Engineering vs 传统软件工程

| 维度 | 传统软件工程 | Harness Engineering |
|------|------------|-------------------|
| **执行者** | 人类开发者 | AI 编码 Agent |
| **关注的"代码"** | 业务代码质量 | Agent 行为质量 + Agent 产出的代码质量 |
| **约束方式** | 规范文档 + Code Review | **机械强制**（运行时守卫、Linter、Hook） |
| **迭代速度** | 天/周级 | 分钟级（子 Agent 并行） |
| **上下文规模** | 一个开发者的认知上限 | 无限（需结构化） |
| **治理粒度** | 文件/函数级 | 操作/Token 级 |
| **核心问题** | "人写对了没有？" | "Agent 被引导好了没有？" |

## 1.5 核心理念体系

Harness Engineering 建立在以下相互关联的原则之上：

### ① Context is Layered, Not Flat（上下文分层）

```yaml
Layer 1 (常驻): CLAUDE.md, AGENTS.md — 项目身份、核心约束
Layer 2 (按需加载): 模块文档、架构决策记录
Layer 3 (动态注入): 当前任务相关文件、最近修改记录
Layer 4 (检索触发): RAG 查询、语义搜索
```

### ② Tools are Governed Capabilities（工具是受治理的能力）

工具按风险分级：

```
READ（读文件）          → 自动授权
WRITE（写文件）         → 自动 + 事后审计
EXECUTE（执行命令）     → 需审批 + 沙箱
CRITICAL（网络/敏感操作）→ 明确授权 + 审计日志
```

### ③ Architecture is Enforced Mechanically（架构被机械强制）

> 传统：文档写"service 层不能直接调用 repository"  
> Harness：Linter + Hook 禁止这种调用 → 违反即阻断

### ④ Entropy Management as GC（熵管理 = 垃圾回收）

Agent 长期工作中产生的**上下文碎片、无效规则、重复工具**需要定期清理：

- 检测上下文膨胀 → 压缩/归档
- 发现冲突指令 → 告警/消解
- 识别失效工具 → 标记/移除

### ⑤ Feedback Must Include Fix Instructions（反馈要包含修复指令）

Agent 的错误反馈不应是"命令执行失败了"，而应是：

```
❌ 错误: Permission denied
✅ 修复指令: 
  1. 在项目根目录运行 `npm install` 
  2. 这将在 node_modules 中安装缺失的依赖
  3. 然后重新运行测试
```

## 1.7 何时需要引入 Harness

| 指标 | 阈值 | 行动 |
|------|------|------|
| 团队有 ≥2 人使用 Agent 编码 | ≥2 | 统一 Harness 规范 |
| Agent 生成代码>30% 的提交 | >30% | 引入质量门禁 |
| 出现过 Agent 导致的破坏性变更 | ≥1次 | 引入安全护栏 |
| 项目代码量 >10 万行 | >100K | 引入结构化上下文管理 |
| 多人协作同一 Agent 项目 | 是 | 引入记忆和上下文共享 |
